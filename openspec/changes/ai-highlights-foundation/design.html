Design proposal · 2026-10-08 · foundation implemented; integration pending

Make an exceptional sound visible

Save a precisely timed manual musical event and compile a supported lighting treatment through the real xLights export path, with persistent intent and reproducible replay.

First slice of AI Highlights. Existing software remains the baseline. This proposal supplies contracts and manual generation before automatic detection or API-backed direction. Typed records, sidecar storage, synthetic fixtures, and the manual-event API are implemented. Two initial recipes compile through XSQ serialization; live generation context and enabled-state export are also implemented. Public plan acceptance, preview integration, and visual acceptance remain pending. See the live replay detail. See the compiler detail. See the manual endpoint contract.

Contracts and identity

Add a small src/highlights/ package using the project's existing Python/dataclass conventions. Validation must reject booleans masquerading as timestamps, nonfinite values, unknown enum values, malformed identifiers, and times outside the recording. Do not add a provider dependency to these records.

RecordProposed contents and invariants
MusicalEventStable event ID; source SHA-256; source revision; event type; start, optional measured peak, and end; timing/evidence provenance; separate detection and salience scores. Manual events may lack detector scores. A point event may have equal times; sustained events require positive duration.
EventReviewAccepted/dismissed state, manual timing/importance overrides, locks, and revision. Preserve original measured data. Manual IDs remain stable on edits; automatic IDs later have explicit revision scope.
HighlightTreatmentReferenced event, allowed recipe ID/version, eligible target selection, bounded intensity, palette source, and bounded event-relative offsets. No arbitrary XML, executable code, filesystem paths, or user-provided effect parameters.
AcceptedHighlightPlanSchema/recipe versions, plan ID/revision, immutable event snapshots, treatments, input fingerprints, source provenance, and status. No provider credentials. Accepted output references the exact reviewed event revision.
ValidationResultMachine-readable issues with event/treatment IDs and severity. Invalid required operations reject the proposal as a whole. No partial mutation of a valid accepted snapshot.

Keep manual state independent of HierarchyResult in this slice. P2 will design the detector-to-event adapter and any hierarchy schema extension, including cache-version invalidation. Old hierarchies remain usable for baseline/manual operation; absent automatic events mean unavailable evidence, not a claim that a song has none.

The current UI identifies Funshine as b98b226927367a97, while its hierarchy uses an MD5 content hash. Use explicit SHA-256/MD5 field names and verify source bytes; never interpret a shortened song ID as the hierarchy hash.

Fingerprint the source audio, normalized reviewed sections, effective theme/slider choices, resolved layout membership, recipe/effect catalog contents, baseline configuration, and variation seed. Ignore presentation-only metadata where it has no generation effect. Changes to generation-relevant inputs make the accepted snapshot stale. A schema version alone is insufficient cache identity.

Persistence and manual APIs

Use <state-home>/library/songs/<song-id>/highlights.json, resolved through existing state path helpers. The sidecar contains a schema version, monotonically increasing revision, reviewed events, draft plan, accepted plan, and prior accepted revision needed for undo. Keep the history bounded. Missing file means highlights disabled; corrupt/unsupported data produces an explicit recoverable error.

This choice avoids losing state when analysis._analyze_in_background or commit_analyze replaces the ordinary session JSON. It introduces an explicit backup obligation: current session-only bundles will not capture this file. Portable bundle support remains a required P1.3/P7.4 task before a release; do not advertise backup completeness in the first internal slice.

Proposed routeBehavior
GET /api/v1/songs/<id>/highlightsReturn current sidecar revision, reviewed events, draft/accepted plan metadata, and computed validity/staleness. Unknown song: 404. Missing sidecar: empty disabled state.
PUT /api/v1/songs/<id>/highlightsAccept expected_revision plus explicitly typed edits/plan acceptance. Validate against the song's current source, context, and catalogs. Revision mismatch: 409. Invalid contract: 400. Invalid references/stale context: 409 or 422 with an actionable issue code.

Snapshot input context before validation, then compare it again at commit. Use an in-process per-song lock plus atomic file replacement for the supported single-backend-per-state-directory deployment. Tests must prove one winner for competing same-revision requests. This is not a cross-process locking guarantee; multiple backend processes sharing one state directory require a separate locking design.

Reanalysis preserves manual events. Existing accepted snapshots become stale when their source/structure/configuration fingerprints differ. Automatic ID remapping is deferred; never silently attach an existing review to a different detected sound.

Compilation through the actual export path

  1. The export endpoint loads and snapshots accepted highlight state alongside the ordinary session. Explicit disabled mode uses the baseline.
  2. Add optional parameters at the end of generator_runner.run and its private pipeline helper. Pass the snapshot into new defaulted GenerationConfig fields.
  3. Build the existing baseline with current seed, theme selection, ordinary accents, curves, transitions, and start/end fades.
  4. Assemble the baseline SequencePlan. Validate the entire highlight snapshot against current inputs before applying it.
  5. Compile into a dedicated default-empty SequencePlan.highlight_effects collection, using ordinary EffectPlacement records. First-slice recipes do not mutate background placements.
  6. The writer includes this collection in its normal placement gathering. Do not rely on the writer's overlap trimming to decide musical conflicts.
  7. Export/package as before. Surface stale/invalid accepted plans explicitly; preserve the prior accepted state and require an explicit baseline export choice rather than silently claiming enhanced output.

Initial recipes: sustained wash/sweep (an envelope-following wash or verified spatial sweep) and isolated impact (a short valid pulse/impact using real catalog definitions). First validate the chosen effect's actual parameter names, target suitability, buffer style, and rendering behavior. Require a measured/manual peak for a peak-anchored recipe; do not invent one for an imported point mark.

Resolve existing eligible groups/props; do not create dangling group names. Inherit the reviewed theme palette. Avoid imported-video targets, singing faces, and other protected active content. Compare underlying physical memberships, not just group names. If every eligible target conflicts, return a useful rejection instead of silently placing an invisible treatment.

Source event timing remains unchanged. Resolve event-relative anchors, bound to the recording, then quantize to the plan's frame interval using one documented rounding policy. Reject a recipe if clamping/rounding leaves insufficient duration. The current default is 25 ms; do not hardcode it into event data. Record resolved placement times for debugging.

Reserve layers in front of relevant existing content only where the target's compositing rules permit it. Code history records that lower indices render in front; actual xLights output must confirm this. Avoid start/end fade regions in the initial slice. Controlled background dimming, its restoration, and richer conflict arbitration belong to P4.3 and must be designed before activation.

Section preview currently constructs a new scoped plan and primarily reads section effects. Forward scoped highlight effects and include accepted-plan identity in preview cache inputs; otherwise an export can contain a highlight that preview silently omits. Preserve other preview behavior in this focused change.

Validation and pre-mortem

This is a direct design review; no unavailable pre-mortem skill or agent review is claimed.

  • Hidden assumption: a point mark has a meaningful peak/end. Require timing evidence for sustained recipes; permit missing measurements rather than fabricating them.
  • Hidden assumption: a visible event is necessarily important. Preserve listener importance separately from detection scores and compare against routine-pattern negatives.
  • Hidden assumption: app IDs are audio hashes of the same kind. Verify actual bytes and distinguish SHA-256, shortened song IDs, and hierarchy MD5 explicitly.
  • Hidden assumption: a group name is a unique physical region. Resolve member overlap and protected content before target selection.
  • Hidden assumption: the preview displays everything the writer exports. Thread and scope the new song-level collection through preview and its cache.
  • Test gap: native baseline lacks several analyzers. Keep capability-specific baseline results and require a deployment/render check before declaring the first slice complete.
  • Test gap: sidecar state is absent from current bundles. Keep backup support visibly pending and test it in P1.3/P7.4 before release.
  • Recovery risk: accepted plan becomes invalid after settings change. Compute staleness from current context and reject enhanced export explicitly; never silently discard user choices.

Tests should cover strict data types, unsupported versions, save/reload, old/no-highlight songs, revision races, no eligible targets, source mismatch, out-of-bounds/off-beat timing, layer order, end-fade conflicts, empty-plan no-op, repeated export equality, preview inclusion, and endpoint forwarding. Use repository state-isolation conventions. Run the applicable existing generator/API/storage checks, then a real xLights render for the manual event.
